# Relay для обхода белых списков

Когда мобильный оператор включает режим **белых списков**, телефон может достучаться только до серверов из разрешённого списка (Яндекс, VK, Госуслуги, часть российских хостингов). Telegram и Cloudflare в этот список не входят, поэтому ни настройки прокси, ни разрез TLS, ни фронтинг на самом телефоне это **не обходят** — пакеты просто не доходят до адресата.

Выход — маленький relay на сервере, чей IP в белый список **входит**:

```
Telegram → TG WS Proxy (телефон) → relay (разрешённый IP) → датацентр Telegram
```

Relay получает уже зашифрованный MTProto-трафик и пересылает его в Telegram как есть — содержимого переписки он не видит. Протокол тот же, что у Cloudflare Worker из десктопной версии (`/apiws?dst=IP&dc=N`), так что приложение может работать и с Worker'ом, и с этим relay.

## 1. Сервер

Нужен VPS с Linux и Python 3.8+ у хостера, чьи адреса открыты у вашего оператора в режиме белых списков. Список меняется и зависит от региона и оператора — проверьте заранее: при включённых белых списках откройте с телефона сайт или IP сервера. Часто подходят адреса крупных российских облаков (Yandex Cloud, VK Cloud, Selectel и т. п.), но гарантий нет.

Серверу самому нужен доступ к Telegram (к адресам `149.154.160.0/20`, `91.108.0.0/16` и др. на порт 443). Российские серверы обычно имеют его без ограничений, так как белые списки применяются только к мобильным абонентам.

## 2. Запуск

```bash
curl -O https://raw.githubusercontent.com/DANILCHT/TG-WS-Proxy-Android/main/relay/tg_ws_relay.py
python3 tg_ws_relay.py --port 8080 --key ПРИДУМАЙТЕ_ПАРОЛЬ
```

Обязательно задайте `--key`: без него relay сможет использовать кто угодно (адреса назначения всё равно ограничены сетями Telegram — открытым прокси он не станет).

### Как служба systemd

```bash
sudo cp tg_ws_relay.py /opt/tg_ws_relay.py
sudo cp tg-ws-relay.service /etc/systemd/system/
sudo nano /etc/systemd/system/tg-ws-relay.service   # впишите свой RELAY_KEY
sudo systemctl enable --now tg-ws-relay
```

### В Docker

```bash
docker build -t tg-ws-relay .
docker run -d --restart=always -p 8080:8080 -e RELAY_KEY=ПАРОЛЬ tg-ws-relay
```

### С TLS (рекомендуется, если есть домен)

```bash
python3 tg_ws_relay.py --port 443 --cert /etc/letsencrypt/live/relay.example.ru/fullchain.pem \
    --keyfile /etc/letsencrypt/live/relay.example.ru/privkey.pem --key ПАРОЛЬ
```

Можно и за nginx: проксируйте `location /apiws` на `127.0.0.1:8080` с `proxy_http_version 1.1`, `Upgrade` и `Connection "upgrade"`.

Проверка: `curl http://IP:8080/healthz` должен ответить `OK`.

## 3. Приложение

**Обход белых списков (relay)** → **Адреса relay**, по одному в строке:

| Вариант | Строка |
| --- | --- |
| Без TLS, по IP | `ws://203.0.113.7:8080?key=ПАРОЛЬ` |
| С TLS и доменом | `wss://relay.example.ru?key=ПАРОЛЬ` |
| Домен, но подключаться к конкретному IP | `wss://relay.example.ru?ip=203.0.113.7&key=ПАРОЛЬ` |
| Сеть проверяет SNI: показать разрешённое имя | `wss://relay.example.ru?ip=203.0.113.7&sni=vk.com&verify=0&key=ПАРОЛЬ` |
| Самоподписанный сертификат | `wss://203.0.113.7?verify=0&key=ПАРОЛЬ` |

Параметры: `ip` — куда подключаться вместо DNS-имени, `sni` — имя в TLS, которое видит сеть, `key` — пароль relay, `verify=0` — не проверять сертификат (трафик Telegram всё равно зашифрован самим Telegram).

Включите **Relay в приоритете**, если мобильный интернет работает только в режиме белых списков: приложение будет сразу идти через relay и держать для каждого датацентра готовое соединение. Без этого переключателя relay просто участвует в «гонке» маршрутов и используется, когда он быстрее остальных.

Кнопка **Проверить соединение** покажет, доступен ли relay и не включены ли белые списки.
